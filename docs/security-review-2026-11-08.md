# Security review — 8 November 2026

This review covers the GetOpenPrism source, dependency graph, available Git history, and the application boundaries for guest chat, authenticated workspace data, AI providers, remote browsing, uploads, and payments. It records preventive changes and their limits. Completed checks appear in [Verification evidence](#verification-evidence); the native Sites version/deployment record identifies the published source. Source changes alone do not establish that production runs the reviewed version.

## What the research supports

**No credible universal evidence was found that a particular top 20 issues causes 99% of incidents in sites like GetOpenPrism.** The checklist below is a practical selection for this application, not a measured frequency ranking or a promise to prevent a percentage of attacks.

The [OWASP Web Top 10:2025](https://top10.owasp.org/2025/), [API Security Top 10:2023](https://api-security.owasp.org/editions/2023/en/0x11-t10/), and [OWASP GenAI guidance](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/) identify important risk classes. Their lists cannot be added together to obtain incident coverage. OWASP's [API methodology](https://api-security.owasp.org/editions/2023/en/0xd0-about-data/) expressly says its public data call did not support a relevant statistical analysis of the most common issues; its prevalence ratings used expert consensus. Vulnerability disclosures, dependency advisory matches, and confirmed breaches also have different denominators.

For this service, the most consequential boundaries are access to another person's workspace, use of paid provider capacity, exposure of credentials or private content, and unsafe interpretation of requests or provider output. Prompts, attachments, web pages, model output, callback payloads, and upstream error messages remain untrusted inputs.

## Changes made in this review

These are additions or changes relative to the inspected starting checkout. They are distinct from the safeguards already present, described below.

| Area | Concrete change and purpose | Source |
| --- | --- | --- |
| Browser execution and caching | A fresh 192-bit script nonce is generated for each request. Incoming nonce/CSP headers are replaced before rendering. HTML receives a nonce-based CSP, restricted framing, browser permission restrictions, and safe referrer policy. HTML, RSC, API responses, and redirects receive private/no-store cache controls. HTTPS responses receive HSTS; static asset caching is retained. | [HTTP security](../lib/http-security.ts), [Worker](../build/sites-worker.ts), [layout](../app/layout.tsx) |
| Unused framework mutation surface | Non-GET/HEAD/OPTIONS requests outside `/api` are rejected before framework dispatch. This application exposes mutations through explicit API routes and has no application Server Actions. | [HTTP security](../lib/http-security.ts) |
| Request origin and decoding | Browser mutations require the exact origin and reject cross-site/same-site Fetch Metadata. Exact webhook and scheduler paths retain service-specific verification: the scheduler requires its bearer secret, while webhook handling verifies authoritative provider state and configured signatures/secrets. Request bodies are bounded by actual streamed bytes, canceled on failure, and limited to 30 seconds. Invalid lengths, unsupported encodings/content types, and malformed UTF-8 JSON are rejected before handlers. | [Request security](../lib/request-security.ts), [API route](../app/api/[...path]/route.ts) |
| Account writes and input validation | An atomic D1 limit permits up to 120 account mutations per minute, with one stable quota row per account. Chat fields, attachment IDs, titles, and administrator reconciliation values receive stricter validation. Existing inference and payment limits continue to apply separately. | [Request security](../lib/request-security.ts), [API route](../app/api/[...path]/route.ts) |
| Concurrent uploads | The 100-file cap for `/api/files` text/source uploads is enforced by a conditional database insert, closing the prior count-then-insert race. Rejected or failed inserts attempt to delete the newly uploaded object; storage deletion failures can require orphan cleanup because D1 and R2 are not one transaction. Filenames have control characters removed. Media references retain their separate existing 20-reference cap. | [API route](../app/api/[...path]/route.ts) |
| AI provider transport | Text adapters reject redirects, including redirects that could forward custom API-key headers. Each streamed provider response is capped at 8 MiB, each complete JSON response at 2 MiB, and each answer at 1 MiB of UTF-8 text. Complete JSON decoding rejects malformed UTF-8. These limits supplement the existing token/time limits. | [Provider adapters](../lib/provider.ts) |
| Error disclosure and cancellation | Unexpected transport, parser, database, and stream errors become deliberate public messages. Historical usage/media errors are masked in user-facing responses without deleting ledger evidence; administrator-only troubleshooting endpoints retain their gated diagnostic access. Chat cancellation stops further output and cleanup failures are logged without raw diagnostics. | [API route](../app/api/[...path]/route.ts), [provider adapters](../lib/provider.ts), [media workspace](../lib/media-workspace.ts), [Worker](../build/sites-worker.ts) |
| Media and locks | Video redirects reject malformed addresses and nonstandard ports. Generated PNG dimensions are capped at 4096 × 4096. A finishing media poll releases only its own lock expiry, avoiding deletion of a successor lock. | [Media provider](../lib/media-provider.ts), [media workspace](../lib/media-workspace.ts) |
| Payment provider consumption | Toss responses are limited to 1 MiB of actual streamed bytes and parsed with strict UTF-8. Oversized/malformed responses are treated as uncertain provider outcomes; existing refund holds and retry idempotency are preserved. The existing 15-second timeout and redirect rejection remain. | [Billing](../lib/billing.ts) |
| Dependencies | Direct framework/validation packages and affected transitive dependencies were updated. Connector preview record validation was adapted to the supported Zod 4 syntax while preserving strict permission envelopes. Repeatable security commands were added. | [Package manifest](../package.json), [lockfile](../pnpm-lock.yaml), [package policy](../pnpm-workspace.yaml), [connector validation](../scripts/connector-preview/protocol.mjs) |

The CSP permits specific Google and Toss integrations and permits inline styles needed by the UI. Development alone permits script evaluation and WebSocket connections. The production script policy does not generally permit inline scripts. This is defense in depth; third-party SDK permissions and renderer behavior still require review when integrations change. See the [OWASP CSP guidance](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html).

## Safeguards already present

The starting source already scoped workspace queries and private downloads to the signed-in owner, used parameterized database statements, checked the exact administrator ID, and restricted sign-in return paths. The guest system already used signed, expiring `__Host-` cookies with Secure, HttpOnly and SameSite attributes; separate session/network/site allowances; and the shared lifetime beta budget. These were inspected and retained rather than introduced by this review. See [authentication](../app/chatgpt-auth.ts), [guest chat](../lib/guest-chat.ts), and [beta reservations](../lib/beta.ts).

The existing text renderer escapes content through React and does not render arbitrary model HTML or Markdown images. Link schemes and credentials are constrained. Files and generated artifacts already had size/type limits, private storage, and owner-checked retrieval. Public shares already represented explicit snapshots that can be revoked; they remain bearer links whose transcript text is intentionally visible to recipients. See [Markdown renderer](../components/guest/guest-markdown.tsx), [artifacts](../lib/work-artifacts.ts), and [API routes](../app/api/[...path]/route.ts).

Existing inference accounting used durable reservations, concurrency checks, and conservative handling when provider spending was uncertain. Existing payment code checked order ownership, server prices, consent and policy gates, payment key/amount/currency/state consistency, and authoritative provider responses. It used unique ledger references, atomic writes, test/live separation, durable refund holds and retry keys. Webhook payloads already triggered reconciliation against the current provider state, rather than directly crediting submitted amounts. Optional webhook HMAC verification applies when its security key is configured; deposit callbacks additionally compare the provider's secret. This review does **not** claim that all webhook authentication settings are configured or that replayed delivery is universally rejected. Reconciliation and idempotency prevent repeated legitimate notifications from repeatedly crediting the wallet. See [billing](../lib/billing.ts) and [payment setup](toss-payments-setup.md).

## Tailored 20-category prevention checklist

Numbers organize the review; they do not represent measured prevalence. “Existing” means present in the inspected starting source, and does not mean formally certified. The [Web](https://top10.owasp.org/2025/) and [API](https://api-security.owasp.org/editions/2023/en/0x11-t10/) lists support the general categories; linked specialist guidance supports the additional boundaries.

| # | Risk | GetOpenPrism status and remaining boundary |
| --- | --- | --- |
| 1 | Object ownership / IDOR | Existing owner predicates cover workspace records and private objects. Strict identifiers and attachment validation were strengthened. Every future endpoint must derive ownership server-side; a supplied record ID alone is insufficient. |
| 2 | Privilege escalation / mass assignment | Existing administrator checks and server-owned pricing/identity remain. New chat/title/reconciliation validation rejects unexpected or invalid fields. Future administrative and connector actions need independent server authorization. |
| 3 | Session theft or forgery | Existing guest cookies are signed and expiring. Account identity is supplied by the Sites host. Confirm host session protections and identity-header stripping at the edge; the application does not implement the host's MFA/session service. See [session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). |
| 4 | Secret exposure | Existing server secret storage remains. Provider redirects and public error disclosure were tightened; historical diagnostics are masked in user-facing usage/media responses, while administrator-only troubleshooting retains its gated access. Repository pattern scans are limited evidence, and runtime secret rotation/access review remain operational tasks. |
| 5 | Automated abuse of paid functions | Existing guest/account quotas, durable spending reservations and lifetime beta limits remain. New account write throttling limits broader mutation churn. Distributed bot traffic still needs edge controls and provider billing alerts. |
| 6 | Vulnerable dependencies / supply chain | Direct and transitive fixes reduce recorded advisory matches. Both production and full dependency graphs were inspected because build packages can affect shipped code. One conditional lint advisory remains documented below. |
| 7 | XSS and unsafe model output | Existing escaped text rendering and constrained links remain. New nonce CSP and browser headers add a second boundary. A future HTML/Markdown plugin, arbitrary image renderer, or new SDK can change this result. |
| 8 | SSRF and credential-bearing redirects | Text/Toss requests reject redirects; video follows a restricted storage allowlist without forwarding the provider credential to storage hosts. Existing browser URL checks reject literal/private-looking addresses. Browserless must enforce DNS resolution and network restrictions; string checks alone cannot prove that. See [SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html). |
| 9 | CSRF / origin confusion | Exact-origin browser mutation checks now fail closed when Origin is missing, null or foreign. Hostile Fetch Metadata is rejected. Service routes use their independent controls; no permissive CORS policy was added. See [CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). |
| 10 | Resource exhaustion | Actual request/response bytes, upload deadlines, output text, and generated PNG dimensions are bounded; existing token/time/concurrency limits remain. Application limits do not stop traffic before it consumes edge/network resources. |
| 11 | Unsafe uploads / downloads | Existing text/image format and size restrictions and private retrieval remain. The 100-file text/source cap is now atomic; rejected objects receive a deletion attempt, with orphan cleanup still needed if storage deletion fails. Expanding to PDFs, archives or active document preview requires a new parser/isolation review. See [upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html). |
| 12 | SQL, command or parser injection | Reviewed queries bind values; application chat does not execute user-provided host commands. Strict body/field validation was strengthened. Provider Code Interpreter is a separately bounded tool; model output is never an authorization decision. |
| 13 | Authentication redirect abuse | Existing return-path validation accepts local paths and rejects external/reserved authentication destinations. Authentication redirects now receive no-store policy. Actual login, logout and cookie handling depend on the Sites host. |
| 14 | Private data in caches or shared links | New no-store policies cover HTML, RSC, API and redirects, with no-referrer and noindex on private/share surfaces. Shares still intentionally disclose transcript text to anyone holding the token; revocation cannot erase recipients' copies. |
| 15 | Security misconfiguration / excess surface | New browser permissions, framing, MIME and HTTPS policies reduce exposed surface; unused page mutations are rejected. Configuration gates still control optional services. Runtime access policy, secrets and account permissions require operational verification. |
| 16 | Payment integrity / webhook abuse | Existing owned orders, canonical prices, authoritative snapshots, consent gates, rate limits and idempotent ledger writes remain. New bounded Toss parsing preserves uncertainty holds. Merchant dashboard/webhook configuration must be checked before payment activation. See [payment integration guidance](https://cheatsheetseries.owasp.org/cheatsheets/Third_Party_Payment_Gateway_Integration_Cheat_Sheet.html). |
| 17 | Races and unsafe retries | File quotas and media lock release were corrected; account mutation quotas are atomic. Existing payment reservations/refund retry keys remain. New multi-step workflows need explicit concurrency and ambiguous-outcome handling. |
| 18 | Direct / indirect prompt injection | Existing research instructions identify retrieved material as untrusted; authorization and budgets remain outside the model. Escaped rendering and CSP reduce automatic output-based exfiltration routes. No claim is made that malicious prompts cannot alter answers or persuade users. See [prompt injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html). |
| 19 | Excessive tool permissions / cross-tenant retrieval | Existing capability checks, owner-scoped attachments, tool call caps and host-managed connector grants remain. Zod migration preserves strict invocation/grant schemas. Adding tool writes, new data sources or broader grants needs a separate permission review. |
| 20 | Insufficient detection / recovery | Existing request IDs and structured status/timing logs remain; new failure logs omit raw sensitive diagnostics. Alert routing, log retention, restore tests and an incident runbook are operational work, not established by source review. See [logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html). |

Recorded local scan artifacts are `dependency-security-audit-all-before.json`, `dependency-security-audit.json` (the production baseline), and the `*-after.json` / `*-final.json` files in the runtime working directory. The installed graph can be rescanned with `pnpm audit --json` and `pnpm audit --prod --json`.

Direct updates include Next and its ESLint configuration `16.4.1`, React/React DOM/React Server DOM Webpack `19.2.8`, Vite `8.1.6`, Zod `4.6.6`, Vinext `1.0.1`, and `@vitejs/plugin-rsc 0.5.34`. Affected transitive versions are constrained by explicit overrides in the package policy. The existing seven-day release-age policy and restricted dependency build-script policy remain.

The intermediate findings required three different decisions:

- **Legacy hooks Zod:** `eslint-plugin-react-hooks 7.1.1` supports Zod 4 and imports its v4 API. A parent-scoped override selects `4.6.6`; unrelated Zod 3 consumers are not globally forced across a major version. Connector record schemas were adapted and regression coverage added. See the [official hooks package](https://github.com/facebook/react/blob/main/packages/eslint-plugin-react-hooks/package.json) and [Zod advisory](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5).
- **Bundled Satori:** old `@vercel/og` embeds the renderer, so overriding only the separate Satori package would not reliably repair distributed code. Vinext `1.0.1` selects `@vercel/og 1.0.3` with patched Satori `0.33.5` and supports its HarfBuzz asset. No application OG renderer usage was found, but the supported framework update removes the vulnerable dependency instead of relying on that absence. See the [maintainer's Satori advisory](https://github.com/vercel/satori/security/advisories/GHSA-wx4j-mvgx-mqwp). Registry metadata and integrity-checked tarball inspection confirmed retained exports and compatibility with the current Vite/Cloudflare/React peer ranges; completed build and browser checks are recorded below.
- **Retained minimatch:** `10.2.5` remains through the development ESLint/TypeScript parser chain, under [GHSA-g3hv-75wg-m249](https://github.com/isaacs/minimatch/security/advisories/GHSA-g3hv-75wg-m249). The described amplification requires an attacker-controlled pattern and `optimizationLevel >= 2`. The inspected parser call uses trusted project configuration and `{ dot: true }`, without that optimization setting; no production request path was identified. The patched major version is `11.0.1`, outside the current consumer's declared range. A blanket unsupported major override was avoided. This remains an open moderate advisory to revisit when the upstream consumer updates or its configuration changes; it is not reported as fixed.

## Secret review and unchanged boundaries

A pattern-based secret review of the **31 commits available at the initial checkout (`c6fa8ed592077f01ae811958c430c2383b03e760`)** reported **zero candidate matches**. This means no searched signature matched in that available history. It does not prove absence of credentials in formats outside the patterns, inaccessible branches/history, runtime configuration, provider consoles, logs, artifacts, or external systems; it does not establish whether any credential was previously exposed. No credential was rotated on the basis of this result.

This work does not change the database schema, runtime secret values, site audience/access policy, payment activation policy, pricing, or approved provider spending allowances. The existing public guest experience and authenticated saved workspace remain the intended access model.

## Operational work outside these code changes

| Boundary | Required operator follow-through |
| --- | --- |
| Host identity and edge IP | The application trusts the Sites-provided `oai-authenticated-user-*` headers and uses Cloudflare edge IP metadata for guest network quotas. Verify that the host strips caller-supplied identity/IP headers, authenticates requests, and prevents a direct origin path that bypasses that boundary. A local mock identity is not evidence that this production contract is enforced. |
| Administrator and deployment accounts | Review least privilege and require MFA for accounts that control hosting, Git, providers, databases and payments. Source changes cannot enforce the external accounts' recovery/session policy. |
| WAF, bots and spend monitoring | Configure edge rate/bot controls and provider budget alerts appropriate to the actual traffic. Per-account and per-network quotas limit application spending but do not establish resistance to distributed attacks or denial of service. |
| Remote browser egress | Verify the managed browser's DNS-resolution, rebinding, redirect and subresource network restrictions, including internal/metadata addresses. The application checks URL syntax and an approved Browserless endpoint, but cannot prove the remote fleet's effective network policy from this checkout. |
| Alerts and incident handling | Route repeated authorization failures, quota exhaustion, unexpected provider errors and unusual payment transitions to an operator. Establish log access/retention, secret rotation, triage and recovery procedures without collecting prompt contents or credentials unnecessarily. |
| Backup and recovery | Verify D1/R2 backup coverage, retention and restoration of a representative workspace and accounting state. Neither a passing unit suite nor a successful deployment demonstrates recoverability. |
| Independent testing | Perform an authorized penetration test against the actual host, including multiple-account access, identity-header trust, sharing, auth callbacks, payment sandbox concurrency and configured integrations. Live payment/provider correctness and adversarial LLM behavior require tests beyond mocked transports. |

These are unverified operational boundaries, not claims that the corresponding controls are absent. The [OWASP SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html), [session](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), and [logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) guidance explains why application checks must be paired with deployment and operating controls.

## Verification evidence

New regression coverage exercises missing/hostile origins, chunked and stalled request bodies, malformed UTF-8, concurrent quotas/uploads, forged fields, error disclosure, streamed provider limits, redirect credentials, media locks/dimensions, payment response bounds and uncertain retries, connector schemas, and browser header behavior. Existing ownership, guest, billing and workspace suites remain relevant. Tests use isolated storage and controlled provider transports; they do not establish live provider access, host account security, real payment processing, or an independent penetration-test result.

The security script runs the suites sequentially because their compiler fixtures can share temporary paths. `pnpm run security:check` combines type checking, those tests, and high/critical audit gates. The remaining moderate minimatch advisory is deliberately visible and documented; a passing gate does not mean the full audit contains zero findings.
